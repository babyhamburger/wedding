**User**

帮忙制作一个婚礼现场上使用的，大家扫码就可以上传随手拍摄的现场照片的网页。参考的是 LiveDrop 的设计思路。它把“扫码即传”做到了极致：宾客不用注册、不用下载 App，扫完码直接打开相机，拍完就传，大屏那边实时收到消息，新照片随即出现。如果你不想自己部署，可以了解下它是否有现成的活动创建服务。
第一，上传逻辑要对移动端友好。宾客的体验应该是：扫码 → 浏览器自动打开 → 点击选照片（或直接唤起相机）→ 上传成功。不要设置注册、登录、填写姓名这类门槛，多一步流失率就翻一倍。同时要处理好网络波动：婚礼场地人多，信号和公共 WiFi 经常不稳定。理想的做法是把未完成的上传保存在手机本地，网络恢复后自动续传，或者至少给出明确的失败重试入口。
第二，存储和性能要提前想清楚。照片是几百 KB 到十几 MB 的二进制大文件，不要直接塞进数据库，否则后期查询和备份会非常痛苦。正确的做法是把照片文件存到对象存储（如阿里云 OSS、腾讯云 COS），数据库只存一条轻量的元数据记录（谁传的、什么时间、文件地址）。上传时最好由后端签发一个临时上传凭证，让手机直接传到对象存储，而不是绕经你的服务器，这样速度更快，也不会因为多人同时上传把服务器压垮。
第三，大屏展示要独立于上传页面。 现场投影或 LED 大屏需要的是一个实时照片墙页面，它能自动刷新、轮播新到的照片。这个页面最好能和上传端解耦，即使上传端短时间内出问题，大屏上的照片依然在正常展示。LiveDrop 就是这么做的：照片墙订阅新增消息，审核动作发生后现场页面跟着变化。

## 0. 技术选型验证

主 agent 的倾向整体正确，做以下微调：

| 项 | 结论 | 理由 |
|---|---|---|
| Node + Express | ✅ 保留 Express 4 | 生态最熟、概念最少；Fastify 性能优势在此场景无意义 |
| SQLite | ✅ better-sqlite3 | 同步 API、零异步复杂度；`node:sqlite` 在 Node 20/22 仍偏新，不值得冒险 |
| 存储抽象 | ✅ 保留双 Adapter | 但**本地模式也统一为"申请凭证 → PUT 直传"**（后端开一个 PUT 接收路由），这样客户端代码对 local/OSS 完全一致，只换 URL |
| 原生前端无构建 | ✅ | 3 个静态页面 + 共享 JS，符合一次性系统定位 |
| ws | ✅ 用 `ws` 库，不用 socket.io | socket.io 重、无必要；ws + 轮询降级足够 |
| sharp 缩略图 | ❌ **砍掉** | 客户端已压缩到 ~1600px，大屏直接用；OSS/COS 自带图片处理 URL 参数（`x-oss-process=image/resize,w_400`）可作大屏网格缩略图。少一个原生依赖，部署更稳 |
| 审核 | 简化为"事后撤回" | 婚礼现场默认自动通过，管理页可一键删除/隐藏，不做阻塞式审核队列 |

**最终栈**：Node 20+ / Express 4 / better-sqlite3 / ws / qrcode（服务端生成二维码 PNG）/ 原生 HTML+CSS+JS。共 5 个 npm 依赖，无构建步骤。

## 2. 数据模型

```sql
-- 单表核心。status 生命周期：init → confirmed →（默认即 approved）
CREATE TABLE photos (
  id            TEXT PRIMARY KEY,          -- crypto.randomBytes(8).hex
  file_key      TEXT NOT NULL,             -- OSS object key / 本地文件名 {id}.jpg
  original_name TEXT,                      -- 宾客手机里的原始文件名
  mime          TEXT,
  size          INTEGER,
  width         INTEGER, height INTEGER,   -- confirm 时客户端回传（可选）
  uploader_ip   TEXT,
  status        TEXT DEFAULT 'init',       -- init | confirmed | hidden
  created_at    INTEGER,                   -- ms，init 时间

);
CREATE INDEX idx_photos_wall ON photos(status, confirmed_at);
```

## 3. API 设计（含存储抽象统一）

**Storage Adapter 接口**（lib/storage/*.js 各实现）：

```js
createUpload(id, mime) -> { uploadUrl, method: 'PUT', headers: {'Content-Type': mime}, expires }
getPublicUrl(fileKey)  -> string           // OSS 域名 URL 或 /uploads/xxx.jpg
exists(fileKey)        -> Promise<boolean> // confirm 时校验（OSS 用 HEAD，local 用 fs.access）
delete(fileKey)        -> Promise<void>
```

**HTTP 接口**：

| 方法/路径 | 说明 |
|---|---|
| `POST /api/uploads/init` | body `{fileName, mimeType, size}`；校验 mime∈{jpeg,png,heic→提示转码}、size≤15MB、IP 限速（如 10 次/分钟）；生成 id，调 `adapter.createUpload`，插入 `status='init'` 行；返回 `{id, uploadUrl, method, headers}` |
| `PUT /api/uploads/raw/:id` | **仅 local 模式**挂载：流式写 body 到 `uploads/{id}.jpg`（15MB 上限，超限断流）。OSS 模式下客户端不经过这里 |
| `POST /api/uploads/:id/confirm` | body `{width,height}`；服务端 `adapter.exists()` 校验文件真实存在 → `status='confirmed', confirmed_at=now` → WS 广播；返回完整 photo 对象 |
| `GET /api/photos?since={confirmedAt}&limit=200&status=confirmed` | 大屏初始加载 + 轮询降级用；返回按 confirmed_at 升序数组 |
| `GET /api/admin/photos?limit=200` | 管理页列表（含 init/hidden），需 `x-admin-token` |
| `POST /api/admin/photos/:id/status` | body `{status:'hidden'\|'confirmed'}`，撤回/恢复，广播 `photo.removed` / `photo.added` |
| `GET /qr.png` | 服务端用 qrcode 库把 `PUBLIC_URL` 渲染成 PNG，可直接投屏/打印 |
| `WS /ws` | 连接即发 `{type:'hello'}`；服务端广播 `{type:'photo.added', photo}`、`{type:'photo.removed', id}`；30s 心跳 ping |

**统一关键**：客户端永远执行「init → PUT uploadUrl → confirm」三步，local 模式的 uploadUrl 指向本服务器，OSS 模式指向 bucket——**前端零分支**。

OSS presigned PUT 自签（V1 签名，约 30 行代码，避免引 SDK）：`StringToSign = PUT\n\n{content-type}\n{expires}\n/{bucket}/{key}`，HMAC-SHA1 + 密钥，拼 `?OSSAccessKeyId=&Expires=&Signature=`。COS 同理。Bucket 需配置 CORS 允许 `PUT` from `*`（或站点域名）。

## 4. 客户端上传页关键逻辑（public/js/upload.js + queue.js）

**选图/拍照**：
- 两个按钮：`<input type="file" accept="image/*" multiple>`（相册）和 `<input type="file" accept="image/*" capture="environment">`（直接唤起后置相机）。不用 getUserMedia，避开 HTTPS/权限弹窗问题。
- 页面顶部展示婚礼标题 + 欢迎语，上传成功给全屏"感谢"反馈（撒花/淡入），鼓励转发。

**压缩（compress.js）**：
- `createImageBitmap(file)` → canvas 缩放至最长边 1600px → `canvas.toBlob('image/jpeg', 0.82)`。
- HEIC 处理：iOS Safari 的 `<input capture>` 默认输出 JPEG；相册选 HEIC 时 `createImageBitmap` 在 iOS 可解码、重编码为 JPEG，Android 失败则提示"请截图后再传"。压缩后体积约 300–600KB。

**IndexedDB 离线队列（queue.js）**：
- DB `wallq`，store `items`，keyPath `id`（客户端生成）。记录：`{id, blob, fileName, mime, size, status: 'queued'|'uploading'|'failed', attempts, lastError, createdAt}`。
- **核心原则：先入库再上传，成功才删除**。选图压缩后立即写 IDB，然后尝试上传。
- 上传用 `XMLHttpRequest`（fetch 无上传进度），`xhr.upload.onprogress` 驱动进度条。
- 触发时机：新任务入队时、`window.addEventListener('online')`、`visibilitychange` 回到前台、每 15s 定时器。串行处理（同时最多 1 个上传，避免弱网互相挤占）。
- 重试策略：指数退避 `min(2^attempts * 2s, 60s)`，最多 8 次后标记 failed 停止自动重试。

**失败重试 UI**：
- 页面底部固定"待上传 N 张"徽点条；点开列表显示每张缩略图 + 状态（排队中/上传中 x%/失败原因）+ 单条"重试"按钮 + "全部重试"。
- 失败项提供"删除"以免卡死队列。
- 顶部显示网络状态横幅：`navigator.onLine === false` 时提示"当前无网络，照片已保存在本机，联网后自动继续上传"。

## 5. 大屏照片墙关键逻辑（public/js/wall.js）

- **初始加载**：`GET /api/photos?status=confirmed&limit=200`，渲染网格（懒加载、按 confirmed_at 倒序，最新在左上）。
- **WS 订阅**：连接 `/ws`；收到 `photo.added` 插入 DOM + CSS 动画（scale 0.9→1 + fade 0.6s，或新照片闪光高亮 2s）；`photo.removed` 淡出移除。
- **断线重连**：指数退避 1s→2s→4s…上限 30s；**重连成功后必须 `GET /api/photos?since={本地最大 confirmedAt}` 补拉断线期间的照片**（这是正确性关键，不能只靠 WS）。
- **轮询降级**：连续 3 次 WS 连接失败后，切到 `setInterval` 5s 轮询 `?since=`；期间仍持续尝试 WS，成功即停轮询。
- **轮播模式**：网格/轮播切换按钮（也支持键盘 ↑↓ 或 30s 自动进入）。轮播取最近 N 张，单张全屏 + Ken Burns（CSS `transform: scale(1→1.08)` 10s 动画），5–8s 切换，新照片到达时若当前屏非最新可立即切入并显示"新照片"角标。预加载 `new Image()` 避免黑屏。
- **图片加载失败**：`onerror` 时从 DOM 移除该格子（防止 OSS 文件被删后大屏破图）。
- 页头：婚礼标题、日期、已收照片数、右下角小尺寸 `/qr.png`（宾客现场扫大屏也能传）。

## 8. 部署注意事项

- **推荐方案**：一台 2C2G 云服务器 + 域名 + **Caddy 自动 HTTPS** 反代 Node（Caddyfile 两行）。婚礼当天所有宾客走 4G/现场 Wi-Fi 访问公网域名，`PUBLIC_URL=https://photo.xxx.com`，二维码指向它。OSS 模式需 bucket 开通公网读（或挂 CDN 域名）。
- **备选方案（无公网）**：笔记本跑服务 + 手机热点，二维码用 `http://192.168.x.x:3000`。注意：① 宾客需连同一热点（现场 Wi-Fi 常有 AP 隔离导致互不可达）；② `STORAGE=local`（无外网时 OSS 直传凭证也签得出，但公网 endpoint 宾客访问不到，故必须 local 中转）；③ http 下 `<input capture>` 相机仍可用（非 getUserMedia），但部分安卓浏览器/微信内置浏览器会弹"不安全"提示，提前用现场同款手机实测。
- **HTTPS 影响**：本方案不用 getUserMedia，摄像头唤起不依赖安全上下文；但微信/QQ 内置浏览器对 http 链接拦截、警告较凶，且宾客大概率扫码进微信——**强烈建议公网 + HTTPS**。
- **OSS 细节**：CORS 必须允许 `PUT` 与 `Content-Type` 头；presigned 签名时 Content-Type 与客户端 PUT 头严格一致；上传目录加日期前缀 `wedding/2026-09-23/{id}.jpg`；生命周期规则 90 天后转低频/删除。
- **进程守护**：`pm2 start server.js` 或 systemd；SQLite 文件与 uploads 目录当天备份（`cp data/hunli.db data/hunli.db.bak` 定时）。
- **容量估算**：200 宾客 × 5 张 × 0.5MB ≈ 500MB，任何规格都无压力；限速防刷即可。

## 使用方式

**新增一场婚礼**：打开超管总控台 https://hunli.gohappymore.top/super，输入超管口令登录，点「创建场次」填 slug（如 `zhang-li`）、标题、日期即可。系统自动生成该场的管理口令，页面上直接给出：

- 宾客上传：`https://hunli.gohappymore.top/e/<slug>/upload`（每场独立二维码，可打印）
- 大屏：`/e/<slug>/wall`
- 管理：`/e/<slug>/admin`（用该场自己的口令）

## 隔离机制

- 照片按场次隔离：数据库 `event_slug` 列、OSS 路径 `hunli/<slug>/日期/…`、WebSocket 按房间广播——A 场大屏绝不会收到 B 场的照片
- 各场管理口令独立，跨场操作一律 403/404
- 宾客手机浏览器本地待传队列也按场次隔离（IndexedDB）
- 场次可「停用」：停用后宾客无法上传，但大屏/管理仍可查看历史照片；default 场不可停用
